# План: переход «отчёт → ассистент» (`/check` → `/chat`)

**Дата:** 10.10.2026 · **Решение:** вариант A (ссылка-переход), выбран Евгением · **Исполнитель:** Opus 5.5 · **Ревью:** два независимых (продукт/поведение; код/безопасность/регрессии)

## 1. Зачем

Сегодня `/check?q=…` (прямой путь без LLM) и `/chat` (ассистент) — два несвязанных пути: со страницы отчёта некуда продолжить разговор об этой бумаге, а чат ничего не знает о только что собранном отчёте и введённых пользователем сумме/комиссии/«обещали». Единственный вход в ассистента — карточка на главной.

**Цель:** под отчётом на `/check` — кнопка «Обсудить с ассистентом», которая открывает `/chat` с уже собранным тем же отчётом и теми же вводами, после чего пользователь задаёт вопросы.

**Принципы (не нарушать):** прямой путь остаётся без LLM (модель вызывается только после перехода в чат и только на вопросы пользователя); числа считает движок (`buildCached`/`applyInputs`), паритет «страница ≡ чат»; чат под фичефлагом `SO_CHAT` — без него кнопки нет.

## 2. Пользовательский сценарий

1. Пользователь на `/check?q=RU000A1038V6`, ввёл «вложу 1 000 000», «комиссия 0,3», «обещали 15».
2. Под блоками отчёта (после Worst-case, перед карточкой «Полный отчёт — после входа») — кнопка **«Обсудить с ассистентом»** (`btn btn-outline`) и подпись: «Те же блоки — в диалоге: спросить про риски и термины, пересчитать под другую сумму».
3. Клик → `/chat?q=RU000A1038V6&promised=15&pos=1000000&k=0.3`.
4. `/chat` открывается, в ленте сразу появляется сообщение пользователя **«Проверь RU000A1038V6, обещали 15%»** (отправлено автоматически), затем — те же блоки отчёта с позицией 1 000 000 ₽ и комиссией 0,3% (строки «При позиции 1 000 000 ₽…», «С комиссией брокера 0,3%…»), затем короткий ответ ассистента-шаблона (как при обычном `check_security`).
5. Дальше — обычный диалог («хорошая бумага?», «что такое НКД?», «а если 5 млн?»).

Ветки: `q` → `pick` (несколько выпусков) — чат покажет список выбора, как сейчас; `notfound`/`err` — как сейчас. Если чат выключен (`SO_CHAT=0`) — кнопки нет; прямой заход на `/chat?q=…` при выключенном чате → 404 (как сейчас).

## 3. Контракт передачи

**URL `/chat`** (все параметры опциональны, кроме `q`): `q` (≤ 200 символов, как в `/api/report`), `promised` (число, 0 < x ≤ 100), `pos` (целое ≥ 1000), `k` (0 ≤ x ≤ `CONFIG.kMax`), `price` (0 < x ≤ 200, только если отчёт на `/check` собран по цене пользователя). Десятичный разделитель — точка или запятая (как `/api/report`). Невалидные значения **игнорируются**, не ошибка.

**Первое сообщение чата** (текст, формирует клиент): `Проверь <q>` + (`, обещали <promised>%` если задано). Текст намеренно содержит только то, что гейт надёжно разбирает в одном сообщении (`check_security` + `parsePromise`); сумма/комиссия/цена **не** кладутся в текст (одно сообщение — одно намерение, R2-21/H.2).

**Поле тела запроса `/api/chat`:** `inputs: ReportInputs` (`position_size`, `k_pct`, `promised_pct`, `offer_price_pct`) — клиент шлёт его с первым (автоматическим) сообщением; сервер валидирует zod-схемой (та же `inputsSchema`, что у инструмента `set_inputs` в `lib/tools.ts`, `.partial()`), кладёт в `session.pendingInputs` и применяет **один раз** — при первой сборке отчёта в этой сессии (`check_security` → `report(query, { ...pendingInputs, ...{promised_pct} })`), затем очищает. Невалидный `inputs` → игнорируется (не 400: это не ошибка пользователя). Если `inputs` приходит, когда отчёт уже есть, — игнорируется.

## 5. Краевые случаи и защита

- `q` пустой/слишком длинный → ссылки нет / `/chat` открывается как обычно без автоотправки.
- Ввод с `/check` через `?price=` (ветка «нет цены», отчёт собран по цене пользователя): передать `price`, гейт применит `offer_price_pct` при сборке — проверить, что `buildCached(query, {offer_price_pct})` в чате даёт тот же отчёт, что на `/check` (паритет).
- Двойная отправка: `AutoSend` только при пустой ленте и один раз; обновление страницы `/chat?q=…` создаёт новый `chatId` → новая сессия → повторная автоотправка (ожидаемо, как «новая проверка»).
- Лимиты сняты, но `inputs` из URL — недоверенный ввод: только zod-валидация, никаких строк в текст модели сверх `q`.
- Никаких изменений в том, что видит модель (`digest.ts`) — отчёт в чате тот же.

## 6. Приёмка

1. `npm run -s selftest` OK; `npm run -s -w @so/engine audit -- --baseline` и `npm run -s -w @so/web audit -- --baseline` — exit 0 (ничего не хуже; перевороты вверх допустимы, объяснить); `tsc` в `apps/web`, `packages/blocks`.
2. `npm run -s e2e:chat` (MOCK) — новый сценарий зелёный.
3. Локально `npm run web:dev` (MOCK_LLM=1, SO_OFFLINE=1): `/check?q=RU000A1038V6` → ввести сумму 1 000 000 и комиссию 0,3 → кнопка → `/chat` показывает отчёт с «При позиции 1 000 000 ₽» и «С комиссией брокера 0,3%», `main_pct` совпадает с `/check`.
4. После выката на `heidi` — проверка в браузере на проде тем же сценарием (ОФЗ 26238 и бумага с гейтом ССекьюр_А RU000A10AST0 — в чате тоже должны быть скрыты fees/колл и видна фраза гейта).
