# План устранения замечаний аудита 09.10.2026

Источник: [AUDIT_2026-10-09.md](./AUDIT_2026-10-09.md) — 49 подтверждённых находок, сведённых к корневым причинам.
Инструмент приёмки: **аудит-харнес** `npm run audit` (движок `packages/engine/src/audit/`, веб `apps/web/audit/`). Каждая проверка утверждает **желаемое** поведение: сегодня она RED, после правки — GREEN. `audit/baseline.json` фиксирует статус на день аудита; `npm run audit -- --baseline` показывает, что перевернулось.

## Принципы

1. **Биржевое число — главное, свой расчёт — контроль.** Не прятать `exchange`, когда расходится own; гасить производное от own и показывать сигнал.
2. **Одна величина — одно значение.** Правило (флаг) и показ (строка, цвет блока) читают одно и то же округлённое число.
3. **Эталоны не благословлять вслепую.** После каждого WP — `npm run golden:diff`, в коммит идёт объяснение каждого изменившегося поля; `golden:write` только после ревью диффа.
4. **Порядок — по отдаче на правку** (WP-B и WP-C закрывают больше всего симптомов одним изменением).
5. Харнес сначала (RED), потом правка (GREEN), потом selftest + golden:diff. Проверка, которая GREEN до правки, — ошибка харнеса, не победа.

## Известные ограничения харнеса

Общее: проверки утверждают **результат**, а не форму кода; где форма всё же закреплена (static), это указано. Все unit/fixture/static — без сети и без зависимости от текущего времени; live (R.2–R.4) — только с `AUDIT_LIVE=1`.

**WP-A.** A.3: допуск ±0,1 п.п. по плану; синтетика различает эталон и частичные правки «индекс по объединённому массиву» на ≥ 0,61 п.п. (самопроверка различающей силы даёт ERROR, если фикстура ослабнет). Не покрыты: флоатерная ветка `afterTax`, `k ≠ 0`, сценарии 2/3, налог на остаток к оферте/коллу (удвоение на колле — A.4). A.1 для флоатера сверяет `r0` с опубликованной ISS ставкой `valueprc` (ISS-колонка `facevalue` в coupons/amortizations всегда равна текущему FACEVALUE — номинал конкретного купона из неё взять нельзя).

**WP-B.** После добавления `BondFacts.settleIso` синтетический `lib.facts()` должен получить это поле (по умолчанию = `todayIso`) — иначе движок получит `undefined`; сами проверки B.1–B.5 от имени поля не зависят. B.4 подменяет глобальный `Date` (восстанавливается в `finally`).

**WP-C.** C.2 строже буквы плана: `main ≈ own ±0,005` (следует из «main = own при отсутствии биржевой пары»). Крафтовые снимки `C_*` — копии `rolf_friday`/`veb_zero` с правкой полей `marketdata_yields`/`marketdata`.

**WP-D.** D.1: поле `yield.control_failed` считается только если добавлено и в zod-схему `contract.ts` (иначе `BondReport.parse` его срежет; достаточно фразы в `yield.line`). После WP-A ветка на `sfo_ast0` переключается на «гейт обязан молчать», срабатывание гейта проверяется синтетикой. D.3 (static) — не анализ потока данных: ищет доступ к полю/деструктуризацию `CONFIG.controlFailPp|controlWarnPp` в коде без комментариев и отсутствие литералов 5/0,5 в строках правила control; ложный RED при `require()`/динамическом `import()`, реэкспорте через третий модуль, цепочке переприсвоек > 1 шага, деструктуризации с аннотацией типа, переносе правила из `tools/validate/src/rules.ts`; ложный GREEN при литерале под нейтральным именем. Не утверждается харнесом, но важно для исполнителя: `tools/validate` (`mustHave("ok")` требует панель `fees`, `k_grid.length === 5`) после включения гейта начнёт ронять корректные gated-отчёты — валидатор нужно обновить вместе с WP-D (сделано в WP-D). D.5 (web, расширение плана): строки `digest.worst` про колл распознаются по заголовку элемента до первого «:» (`/досрочн|колл/`), а не по всему тексту — иначе ложное попадание на «Рост ставок: … держать до колла …» после WP-F; own-числа (`own_control`, `k_grid`, pre/post, проценты из текста `worst.call`) ищутся во всех листьях дайджеста вне диагностических строк. D.1/D.5 не покрывают колл без даты при гейте (элемент `call` без own-числа остаётся — veb_zero).

**WP-F.** F.1/F.2 сверяют продукт с продуктом (`k_grid[k=0].pre` ≡ `round2(call.y)`/`own` той же сборки, без допуска); независимый IRR к коллу — только справочно в F.3. Сверка `worst.rates` фактически дублирует `horizon_label` (inputs.ts:163 переписывает текст из него) — несущее утверждение — `k_grid`. F.1/F.3 вызывают `horizon(b)` для справочного текста: смена сигнатуры → ERROR. F.3 — только `control_diff_pp ≤ 0,5` (литерал плана; GREEN достижим одной правкой F — Δ 0,35 от todayIso, ≈0 после WP-B). F.4 распознаёт заглушки форм «с офертой —/?/n/a» и «в эту дату» сразу после «с офертой»; флаг 9 / `worst.reset` для put без даты не покрыты.

**WP-G.** G.1 опирается на имя поля плана `b.tradingOpen`; иной механизм «сессия закрыта» оставит RED при верном поведении. G.2: статическая часть ловит только соседство `gap_pp` и знака сравнения в теле Claim; поведенческая требует классов `tone-bad`/`tone-good`. G.3: элемент `worst.rates` обязан остаться (с `null` и текстом «дюрац… не опубликован»). G.4: содержание details сверх «не приписывает отсутствие заявленной» не утверждается. G.5: эвристика по якорям («кредитн… риск», «риск… эмитента/дефолт», «преми… за риск») и конечному списку слов градации — формулировка без якорей даст ложный RED; при `!fired` сравнение идёт со статическим текстом флага 3, который не рендерится. G.6 не предписывает `<` vs `<=`, только согласованность. G.7: литерал ищется в теле `FlagsScore`; рендер требует класс `note--good`.

**WP-R.** R.5 утверждает обе границы пула (6–10) по времени и `maxInflight`. R.6 — подмена `globalThis.fetch`. R.7-web-schema подменяет импорт `@/lib/engine`: валидация внутри `buildCached` этой проверке не видна (план кладёт `safeParse` в маршрут). R.7-web требует HTTP 4xx для `{kind:"err"}` — принято как существующая конвенция маршрута (пустой `query` → 400). R.8-guard требует реального поиска ISS по названию; alias-кэш без ISS оставит guard RED — тогда пересматривать условие, не продукт. Дочерние процессы `node --import tsx` + `module.registerHooks` — Node ≥ 22.15. Golden/фикстуры ISS возвращают строку РОЛЬФ на любой `q` — объединение токенных поисков без дедупликации по SECID даст `pick`.

**WP-T.** T.1 исполняет `golden:write`/`selftest` во временных копиях движка (симлинки на node_modules/audit-fixtures); якоря мутаций `export function yieldOf(` и `round2(Math.abs(ownCtl - b.moexY))` должны оставаться единственными — иначе ERROR «обнови якорь». T.2 — kind static, но собирает отчёты из фикстур; порог класса F `|clean − колл| ≥ 0,25` — конвенция харнеса. T.3 — `spawn npm`. T.5 — мини-модель `sh`: поддерживает `;`, `&&`, `||`, `X=$?`, `exit $X`, `[ … ]`, `set -e`, `sh -c`, `run-s`, `npm run -ws`; конвейеры, подоболочки, `if/for`, `$(…)`, `concurrently` → RED «проброс не подтверждён»; `\`-продолжение строки трактуется как `;` (ложный RED, консервативно); флаги раннера (`--baseline`) не интерпретируются.

**WP-H.** H.7 требует `usage.cost` от Jev-мока (правка «usage без cost, списание по прайсу в route.ts» даст (a) RED при верном (b) — минимальное завышение, оставлено). H.7-price (static) — только отсутствие `?? 0`/`0.0` сразу за `estimateCost(...)`. H.7/H.7-health завязаны на прайс Jev 0,042 $/1M из `usage-log.ts`. H.2-template и H.6 — эвристики по тексту (одно предложение; маркер «по умолчанию» рядом с позицией). H.5: исключение до `Response` = «не 400». Серверные модули грузятся через resolve-хук `server-only`; `budget.ts` фиксирует `SO_USAGE_DIR` при первом импорте; `fetch` подменён везде.

**WP-S (static).** S.1 распознаёт: `rate_limit` в heredoc-шаблоне Caddyfile `deploy/heidi/setup.sh` (цель записи `/etc/caddy/Caddyfile` ищется в префиксе до `<<` — формы `cat <<EOF | sudo tee /etc/caddy/Caddyfile` и `cat <<EOF > /etc/caddy/Caddyfile` **дадут ложный RED**), признак сборки с модулем `caddy-ratelimit`, либо лимитер в `apps/web/middleware.ts` (числовая константа лимита + адрес клиента как ключ; `fn(ip,…)` засчитывается для любой функции — возможен ложный GREEN). Не распознаёт: per-IP лимитер внутри `route.ts`/lib, внешний WAF/CDN, Caddy JSON, путь через переменную. S.2 распознаёт только явные сравнения `.length`/`Content-Length` с литералом/константой в `if`/`while` с 400/413 в блоке или обрезкой `slice(-N)`; `<`/`<=` принимаются без учёта направления (нижние предохранители `length < 1` могут быть засчитаны), `messages.slice(-1)[0]` засчитывается как обрезка; не распознаёт `reduce`/`join().length`, zod `.max()/.refine()`, middleware, хелперы, тернарники, статус через константу. **Рекомендация для WP-S:** реализовать в распознаваемых формах либо править S.1/S.2 вместе с правкой продукта.
